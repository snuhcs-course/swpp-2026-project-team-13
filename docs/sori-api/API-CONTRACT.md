# SORI API 계약 v0.9.0

## v0.9.0 리듬 Drills 기록

로그인 계약과 기존 Practice/Exam 경로는 유지한다. `POST /api/v1/drills/rhythm/plays/`는 완료·정답 공개·중단된 리듬 미니게임 한 문제의 불변 기록을 저장한다. Bearer 인증과 `Idempotency-Key`가 필요하다. [게임·기록 명세](../RHYTHM-PUZZLE.md), [요청 예시](examples/rhythm-play.json), OpenAPI의 `RhythmPlayRecord`를 따른다.

서버는 앱과 동일한 버전의 카탈로그 해시, 보기 집합, 출처 분석을 확인하고 모든 제출을 소리 기준으로 직접 재채점한다. 첫 제출/힌트 이후 제출을 구분한다. 201 신규 저장, 200 동일 플레이 재전송이며 같은 키나 플레이 ID의 다른 내용은 409다. 409 `RHYTHM_CATALOG_MISMATCH`이면 앱은 기록을 보존하고 서버/앱 버전 일치를 안내한다. `GET`은 자기 기록만 `page` 기준 30개씩 반환한다. 기록과 전송 영수증은 계정 삭제 시 제거된다. 데모는 로컬 저장만 한다.

이 버전은 개인 연습용 iPad 앱과 Django 서버의 계약입니다. HTTP 경로는 /api/v1/을 유지합니다. Practice는 마디별 자기채점, Exam은 OpenRouter에 필기 이미지와 고정된 정답을 함께 보내는 AI 평가·한국어 피드백입니다. 두 모드 모두 기존 재생 계획을 사용하며, 정답을 기기에 전달하지 않는 감독형 시험 구조는 아닙니다.

## Practice / Exam 분리 (2026-11-01)

응시 생성에 `mode: practice | exam`을 추가합니다. 새 앱은 항상 명시하며, 생략한 구버전 요청과 기존 응시는 Exam으로 유지합니다. 생성 후 모드를 바꿀 수 없습니다. `Attempt` 응답에는 `mode`, nullable `feature_analysis_id`가 추가되고, Practice의 `grading_mode`는 `self`입니다. 새 서버 응시는 정답 자산을 검증한 Feature v1 분석 ID를 고정합니다. 과거 응시와 로컬 데모의 분석 ID는 null일 수 있습니다. 분석 준비 실패는 503 `QUESTION_ANALYSIS_UNAVAILABLE`이며 AI를 호출하지 않습니다.

Practice 제출은 **200 PracticeAssessment**를 즉시 반환합니다. 처음은 `status=pending, revision=0, errors=[]`이며 AI 작업을 만들지 않습니다. `GET result/`도 같은 종류의 최신 기록을 반환합니다. `PUT self-assessment/`는 아래 전체 스냅샷을 저장합니다.

```json
{
  "expected_revision": 0,
  "errors": [{"measure": 3, "types": ["pitch", "rhythm"]}],
  "completed": true
}
```

- 마디 번호는 응시 문제의 1-based 범위입니다. 같은 마디는 한 번만 보내며 `pitch / rhythm / other`를 중복 없이 복수 선택합니다. 마디 오름차순, 유형은 위 순서로 정규화합니다.
- `completed=false`는 미완료/임시 저장입니다. `completed=true, errors=[]`는 오류를 찾지 못하고 채점을 완료했다는 별도 관찰입니다. 숫자 점수나 AI 피드백을 만들지 않습니다.
- 저장마다 revision을 1 올린 새 이력 행을 추가합니다. 완료 후 수정도 이전 기록을 보존합니다. 통계의 최신 상태는 해당 응시의 마지막 revision으로 판단해야 합니다.
- `expected_revision`이 최신 값과 다르면 409 `SELF_ASSESSMENT_REVISION_CONFLICT`입니다. 서버 기록을 덮어쓰지 않으며 앱은 로컬 표시를 보관하고 사용자가 서버 표시 적용/내 표시 유지 중 선택하게 합니다.
- 저장에는 `Idempotency-Key`가 필수입니다. 응답 유실 시 **같은 키·같은 본문**을 재전송합니다. 최초 저장 영수증이 반환되므로 이후 수정본을 덮어쓰지 않습니다.
- Practice의 `grading-retries/`는 409 `AI_GRADING_NOT_AVAILABLE`, Exam의 `self-assessment/`는 409 `SELF_ASSESSMENT_NOT_AVAILABLE`입니다.

Exam 제출은 기존 **202 Grading**과 비동기 워커·결과 조회·재시도를 유지합니다. 서버에는 인식 XML 전체와 오류 annotation에 해당하는 마디 XML/유효 attributes를 함께 보관합니다. XML은 인식 결과의 근거이며 실제 오류 위치의 확정 정답이 아닙니다. 인식 불확실 여부를 별도로 남기고, 표기 권장 사항은 오류로 세지 않습니다. 현재 사용자 약점 판정·통계 화면·개인화 프롬프트는 포함하지 않습니다.

화면·저장·수동 확인 절차는 [Practice / Exam 안내](../PRACTICE-EXAM.md), 샘플은 `examples/practice-assessment-*.json`을 참고하세요.

## 고난도 문제 추가 (2026-10-31)

이 절의 최초 추가분은 기본 3개와 고난도 59개, 총 62개입니다. 이후 초·중급과 클래식이 추가되어 현재 일반 113개와 클래식 11개를 제공합니다. 기본 3개의 ID·메타데이터·악보 bytes와 기존 응시 스냅샷은 유지합니다. 목록은 기본 20개씩 페이지를 나눕니다.

고난도 자산은 `sori-monophonic-v3`입니다. 2/4·7/8·9/8·12/8, 32분음표·3단 빔, MIDI 48–95 음역을 추가로 허용합니다. 조표가 없고 조성이 확정되지 않은 원본은 `key_signature.mode=unspecified`로 전달하며 앱에서 ‘조표 없음’으로 표시합니다. `tonic=C`는 준비용 기준음이고 다장조 판정을 뜻하지 않습니다. 해당 main XML은 fifths=0, mode=none입니다.

새 박자도 재생 계획 v4를 사용합니다. 9/8·12/8은 점4분음표=55(범위 48–66), 2/4·7/8은 4분음표=80(범위 72–96)입니다. 스케일은 2/4에서 4마디, 7/8에서 3마디, 9/8·12/8에서 2마디입니다. 마지막 도의 긴 음가는 붙임줄로 나눌 수 있습니다. 새 박자의 권장 시간은 각각 393·443·468·516초이며 예비박은 분모 단위로 한 마디입니다. 최종 정답 PNG는 MXL 해시로 연결합니다. 상세 출처와 재생성 방법은 [고난도 문제 안내](../NAVER-QUESTIONS.md)에 있습니다.

계약 버전은 v0.8.0입니다. OpenAPI의 info.version은 v0.8.0 전체를 구현할 때까지 v0.7.0을 유지합니다. [v0.7.0 로그인 계약](#v070-로그인-계약)에 따른 로그인·로그아웃, 공유 시도 제한과 앱의 인증 복구에 더해, v0.8.0의 [회원가입](#v080-회원가입-계약), [계정 삭제](#v080-계정-삭제-계약)와 [프록시를 거친 요청의 절대 URL과 클라이언트 IP 기준](#통신과-인증)을 구현했습니다. [AI 채점 사용량 상한](#ai-채점-사용량-상한-v080)은 아직 구현 전입니다. 이 항목의 오류 코드는 openapi.json에 x-status: planned로 먼저 반영했으며, 구현 후 이 표시를 제거하고 info.version을 v0.8.0으로 맞춥니다.

이 문서는 앱이 관찰할 수 있는 동작(요청·응답·상태 코드·헤더·오류 코드)을 정의합니다. 로그인·회원가입·계정 삭제·AI 채점 사용량 상한의 서버 내부 구현, 현재 배포 구성, 운영 설정, 배포 점검과 검증 항목은 [AUTH-IMPLEMENTATION.md](AUTH-IMPLEMENTATION.md)에 둡니다. 이 계약은 특정 배포 환경에 의존하지 않으며, 서버를 옮겨도 앱이 바꿀 것은 서버 기준 주소뿐입니다.

## 재생 설정 v4와 문제 버전 2

새 응시는 playback_plan.version=4를 사용합니다. 기존 v2/v3 응시의 저장된 악보·재생 계획은 변경하지 않습니다. 새 앱과 서버를 함께 업데이트한 후 새 응시에서 변경을 확인합니다.

| 박자 | 표시 기준 | 기본값 | 권장 범위 |
|---|---|---:|---:|
| 4/4 | quarter / 4분음표 | 80 | 72–96 |
| 3/4 | quarter / 4분음표 | 80 | 72–96 |
| 6/8 | dotted_quarter / 점4분음표 | 55 | 48–66 |

tempo는 policy_id, beat_unit, bpm, minimum_bpm, maximum_bpm을 포함합니다. 기존 tempo_bpm은 4분음표 기준의 number이며, 6/8 기본값은 82.5입니다. 정수로 반올림하지 않습니다. MIDI에는 마이크로초 단위로 변환해 기록합니다.

템포 정책 원본은 backend/content/playback-settings.json입니다. resolve_tempo가 응시 생성 시 값을 선택하고 plan에 고정합니다. 이후 실력별 선택 로직은 selected_bpm으로 연결할 수 있습니다. 문제 metadata에 정책 기본값을 저장하지 않으므로 기본값 수정이 정답 버전의 불변성을 깨지 않습니다. 정책 수정 후 python scripts/build_question_assets.py로 데모의 TempoDefaults.swift를 갱신합니다.

악보의 source_tempo_bpm=96은 원본 표기 검증용이며 실제 재생 속도와 분리합니다. 생략된 기존 자산은 96으로 해석합니다. 악보 해시·마디·음표·중간 템포 변경 검사는 유지합니다.

문제 버전 2의 스케일은 C4 D4 E4 F4 G4 A4 B4 C5 B4 A4 G4 F4 E4 D4 C4입니다. 처음 14음은 8분음표이고 마지막 도는 마디 끝까지 유지합니다. 4/4는 2마디, 3/4·6/8은 3마디입니다. scale.to_measure와 score_assets.scale.measure_count를 따르며 2로 고정하지 않습니다. 새 권장 시간은 4/4 456초, 3/4 426초, 6/8 423초(올림)입니다.

새 instrument_profile_id는 sori-piano-v2입니다. 원본 현 진동·해머 어택·감쇠를 합성한 피아노형 SF2이며 실제 피아노 녹음은 아닙니다. v1 음원과 자산을 보관해 기존 응시를 지원합니다. 별도 외부 음원 다운로드나 라이선스 의존성은 없습니다.

## 통신과 인증

- 일반 요청·응답은 application/json, snake_case이며 성공 객체를 직접 반환합니다.
- 개발 도구 토큰, 로그인 토큰, 회원가입으로 발급한 토큰 모두 Authorization: Bearer <token>을 사용합니다.
- UUID, UTC ISO 8601 날짜, 모든 응답의 X-Request-ID를 사용합니다.
- 개인 API·MXL·제출 이미지는 인증하고 Cache-Control: private, no-store를 사용합니다. 다른 사용자의 응시·답안은 404입니다.
- 경로의 마지막 /를 포함합니다. 인증 자산은 API와 같은 origin이고 리다이렉트하지 않습니다.
- iPad의 Debug 빌드는 LAN HTTP를 허용합니다. Release는 HTTPS를 요구합니다.
- v0.8.0부터 응답에 넣는 절대 URL(자산 url, image_url, template_png_url, 목록의 next·previous, Location)은 그 요청을 받은 공개 origin(scheme·host·port)을 사용합니다. 서버 앞단의 HTTPS 프록시를 거친 요청에는 https://<공개 호스트>를, 프록시 없이 직접 받은 요청에는 그 연결의 scheme과 주소를 사용하므로 앱은 기준 주소와 같은 origin의 URL을 받습니다.
- 서버 앞단의 프록시는 서버가 응답하지 못하거나 요청을 차단하면 이 계약의 형식이 아닌 오류(HTML 본문, X-Request-ID 없음)를 반환할 수 있습니다. 앱은 본문을 해석할 수 없는 401 이외의 오류 응답을 error.code로 분기하지 않고 상태 코드와 관계없이 서버 연결 문제로 안내하며, 이 응답으로 인증 상태를 바꾸지 않습니다. 서버가 보내는 401은 항상 이 계약의 형식입니다.
- 로그인·회원가입의 IP별 시도 제한은 서버가 판정한 클라이언트 IP를 기준으로 합니다. v0.8.0부터 서버가 신뢰하도록 설정한 프록시를 거친 요청은 그 프록시가 전달한 접속 IP를, 그 외 요청은 서버에 직접 연결한 주소를 사용합니다. 클라이언트가 임의로 넣은 X-Forwarded-For 등 전달 헤더는 사용하지 않습니다. IPv4는 주소 단위, IPv6는 /64 네트워크 단위로 집계합니다. 학교 Wi-Fi처럼 같은 공인 IP를 쓰는 사용자들은 하나의 IP 한도를 함께 사용합니다.

## v0.6.0: 정답 이미지, 표기 관습, 악기 음색

문제 상세·응시의 question에 선택 필드 correct_score가 추가됩니다. url, content_type=image/png, sha256, size_bytes, pixel_width, pixel_height, renderer를 포함합니다. GET /api/v1/questions/{id}/versions/{version}/display/는 Bearer 인증과 Accept: image/png를 사용하며 기존 악보 파일과 같은 버전 접근 규칙을 적용합니다. 원본 main.mxl의 SHA-256으로 사전 생성 이미지를 연결하므로 DB 문제 metadata와 응시 스냅샷을 수정할 필요가 없습니다. 현재 개인 연습용 client_readable_practice 정책은 유지됩니다.

정답 이미지는 MuseScore Studio 4.6.3 + scripts/engraving/compact-v1.mss로 사전 생성합니다. 마디 번호 없이 4+4마디 두 줄이며, 직전 마디의 변화음을 환기하는 주의 임시표를 표시용 사본에 추가합니다. 원본 MusicXML·재생 데이터·채점 기준은 수정하지 않습니다. 앱은 PNG 바이트·해시·크기를 검증하고 응시별로 캐시합니다. 미리보기 생성은 서버 요청/LLM 대기 경로 밖에서 수행합니다.

annotations.type에 notation_error(표기 관습 오류), notation_suggestion(권장 표기)을 추가합니다. note_index와 end_note_index는 선택 가능한 nullable 정수(1~128)로 마디 안의 음표/쉼표 순서이며, 마지막 순서는 첫 순서 이상이어야 합니다. 기존 기록에는 두 필드가 없습니다. bbox는 여전히 제출 전체 이미지의 마디 범위이며 음표 좌표가 아닙니다. 프론트엔드는 선택한 피드백의 마디만 강조하고, 설명에 음표 순서를 표시합니다.

새 채점 프롬프트 버전은 sori-feedback-2-notation-1입니다. grading-prompt-v2.txt + notation-rules-v1.txt 전문을 각 GradingJob에 저장합니다. 호출은 기존과 같은 이미지+정답 1회이며 자동 유료 재시도는 없습니다. 권장 제자리표 생략과 빔 묶음 지적은 이번 버전에서 음정·리듬 점수에 추가 감점하지 않습니다. 실제 음높이·길이 오류와 별도로 설명합니다. 규칙을 프롬프트에 넣었다고 인식 정확도를 보장하지 않으며 실제 필기 평가는 별도 검증이 필요합니다.

음색은 사용자 기기의 로컬 선호입니다. 기존 playback_plan의 악보·템포·대기 시간·예비박 계약은 변경하지 않습니다. 악기 프로필은 문제의 원본 기본값이며, 앱 설정의 GeneralUser GS 프리셋이 실제 문제/스케일 음색을 선택합니다. 음색 ID는 서버에 전송하거나 점수에 사용하지 않습니다.

## v0.7.0 로그인 계약

### 로그인 범위와 공통 규칙

아이디·비밀번호로 로그인하고 기존 Bearer 인증을 사용하는 개인 연습용 MVP 계약입니다. v0.7.0에서는 계정을 관리자가 사전에 생성합니다. 회원가입은 [v0.8.0 회원가입 계약](#v080-회원가입-계약)에서 추가하며, 소셜 로그인, 비밀번호 재설정 API, 기기별 세션 및 refresh API는 범위에 포함하지 않습니다. HTTP 경로는 계속 /api/v1/을 사용합니다.

- 로그인은 인증 없이 호출합니다. 서버는 이 엔드포인트에서 Bearer 인증을 수행하지 않으므로, 남아 있는 잘못된 Authorization 헤더가 새 로그인을 차단하지 않습니다. 앱은 로그인 요청에 해당 헤더를 보내지 않습니다.
- 로그인 요청·성공 응답은 application/json이며 성공 객체를 직접 반환합니다. 로그아웃 성공은 본문이 없습니다.
- 성공·오류·204 응답 모두 X-Request-ID와 Cache-Control: private, no-store를 포함합니다. 오류 본문의 request_id는 X-Request-ID와 같습니다.
- 비밀번호와 토큰은 URL·쿼리·로그·분석 이벤트에 기록하지 않습니다. 비밀번호는 서버에서 Django 비밀번호 검증 기능으로 확인하고 평문으로 저장하거나 응답하지 않습니다.
- 로그인·로그아웃에는 Idempotency-Key가 필요하지 않으며, 기존 응시 API의 멱등성 영수증 저장 대상에도 포함하지 않습니다.

| 메서드 | 경로 | 인증 | 성공 | 동작 |
|---|---|---|---|---|
| POST | /api/v1/auth/login/ | 불필요 | 200 | 아이디·비밀번호 확인 후 토큰과 프로필 반환 |
| POST | /api/v1/auth/logout/ | Bearer | 204 | 해당 사용자의 토큰 폐기, 응답 본문 없음 |
| GET | /api/v1/me/ | Bearer | 200 | 기존 API로 로그인 상태·프로필 확인 |

### 로그인: POST /api/v1/auth/login/

요청 본문은 아래 두 필드만 갖는 JSON 객체입니다. 배열, null, 알 수 없는 필드, 누락·빈 문자열·잘못된 타입은 400 VALIDATION_ERROR입니다. 문법이 깨진 JSON도 같은 오류를 반환합니다.

로그인 본문의 크기는 JSON 파싱 전 UTF-8 요청 본문 기준 최대 32 KiB(32768 bytes)입니다. Content-Length 유무와 관계없이 같은 상한을 적용하며, 초과하면 필드 길이 오류인 400과 구분해 413 REQUEST_TOO_LARGE를 fields=[]로 반환합니다. 본문 크기 제한은 아래 시도 제한과 입력 검증보다 우선하며, 이 단계에서 거절한 요청은 로그인 시도 횟수에 포함하지 않습니다. 기존 이미지 업로드용 IMAGE_TOO_LARGE 코드는 로그인에 사용하지 않습니다.

| 필드 | 타입 | 필수 | 규칙 |
|---|---|---|---|
| username | string | 예 | 1~150자. 이메일이나 표시 이름이 아닌 계정 아이디이며 대소문자를 구분합니다. |
| password | string | 예 | 1~1024자. 가입 시 비밀번호 정책을 로그인 검증에 다시 적용하지 않습니다. |

앱과 서버는 두 필드의 앞뒤 공백 제거, 대소문자 변환 등 입력값을 바꾸는 처리를 하지 않습니다. 올바른 형식의 미등록 아이디나 틀린 비밀번호는 400이 아닌 401 INVALID_CREDENTIALS입니다. 인증 API의 문자열 길이는 모두 유니코드 코드 포인트 수로 셉니다. 회원가입에도 같은 기준을 적용합니다.

```json
{
  "username": "student01",
  "password": "example-password"
}
```

성공 시 200과 아래 객체를 반환합니다. 모든 필드는 필수입니다. access_token은 비어 있지 않은 불투명 문자열이며, 앱은 길이·내부 구조·JWT 여부에 의존하지 않습니다. token_type은 항상 Bearer입니다.

```json
{
  "access_token": "<발급된 토큰>",
  "token_type": "Bearer",
  "user": {
    "id": "11111111-1111-4111-8111-111111111111",
    "display_name": "청음 학습자",
    "learning_goal": "college_entrance"
  }
}
```

user는 기존 UserProfile과 같은 스키마입니다. id는 /me/에서 반환하는 UserProfile의 UUID이며 Django 사용자 테이블의 내부 ID가 아닙니다. 프로필이 없다면 생성해 반환하고, 이후 로그인에도 같은 UUID를 유지합니다. 응시 소유권은 서버가 인증한 사용자로 결정하며 요청 본문에서 사용자 ID를 받지 않습니다.

### 토큰 수명과 폐기

기존 DRF Token 모델을 재사용해 사용자당 유효 토큰 하나를 유지합니다. 유효한 기존 토큰이 있으면 재로그인 시 같은 토큰을 반환하고, 없으면 새로 생성합니다. 동시 로그인도 사용자당 하나의 토큰과 하나의 프로필을 유지해야 합니다.

- 이 MVP의 토큰은 자동 만료되지 않습니다. expires_in, expires_at, refresh_token은 반환하지 않습니다. 앱 종료·재실행으로 서버 토큰이 폐기되지 않습니다.
- 여러 기기에서 같은 계정으로 로그인하면 토큰을 공유합니다. 한 기기에서 로그아웃하면 모든 기기의 해당 토큰이 무효화됩니다.
- 로그아웃, 관리자에 의한 토큰 회수, 비밀번호 변경·재설정, 계정 비활성화 시 토큰을 폐기합니다. 비활성 계정은 기존 토큰으로도 인증할 수 없습니다. 계정을 다시 활성화해도 폐기한 토큰은 복구하지 않습니다.
- 폐기 후 재로그인하면 다른 토큰을 발급합니다. 폐기 응답 이후 새로 인증하는 보호 API 요청은 이전 토큰으로 접근할 수 없으며, 이미 인증해 처리 중인 요청을 소급 취소하지는 않습니다.

비밀번호 변경·재설정 또는 계정 비활성화와 로그인이 겹치면, 변경 전 비밀번호나 비활성화 전 상태만 검증한 요청이 변경 완료 후 유효 토큰을 발급해서는 안 됩니다. 변경 완료 전에 발급된 토큰도 해당 변경 작업에서 함께 폐기합니다. 이 규칙은 지원하는 관리자 비밀번호 변경·재설정 및 비활성화 경로 모두에 적용합니다.

기기별 로그아웃이나 자동 만료가 필요해지면 별도 세션 모델과 갱신 계약을 추가해야 합니다. 이 MVP 계약에 기기별 로그아웃 또는 자동 갱신을 구현한 것으로 간주하지 않습니다.

### 로그아웃: POST /api/v1/auth/logout/

Authorization: Bearer <access_token>을 보내며 요청 본문은 없습니다. 서버는 요청 토큰과 일치하는 현재 토큰을 폐기한 뒤 204를 반환합니다. 사용자·프로필·응시·답안은 삭제하지 않습니다.

앱은 204를 JSON 본문 디코딩이나 Content-Type 헤더 존재 여부 검사 없이 로그아웃 성공으로 처리합니다.

토큰 누락·잘못된 토큰·이미 폐기한 토큰은 401 AUTHENTICATION_REQUIRED입니다. 따라서 성공한 로그아웃을 같은 토큰으로 반복하면 401이며, 앱은 이 경우도 해당 토큰이 유효하지 않은 상태로 처리합니다. 토큰 폐기와 재로그인이 겹쳐도 이전 토큰의 로그아웃 요청이 새 토큰을 폐기해서는 안 됩니다.

### 오류와 로그인 시도 제한

오류는 기존 error(code, message, fields, retry_after_ms), request_id 형식을 사용합니다. 앱은 message 문구가 아니라 HTTP 상태와 error.code로 분기합니다. 모든 401 응답에는 WWW-Authenticate: Bearer를 포함합니다.

| HTTP | error.code | 조건 |
|---|---|---|
| 400 | VALIDATION_ERROR | JSON 문법·필드·타입·길이 규칙 위반 |
| 401 | INVALID_CREDENTIALS | 미등록 아이디, 비밀번호 불일치, 비활성 계정, 사용 가능한 비밀번호가 없는 계정 |
| 401 | AUTHENTICATION_REQUIRED | 로그아웃·/me/ 등 보호 API의 토큰 누락·무효 |
| 405 | METHOD_NOT_ALLOWED | 지원하지 않는 메서드 |
| 413 | REQUEST_TOO_LARGE | 로그인 본문이 32 KiB 초과 |
| 415 | UNSUPPORTED_MEDIA_TYPE | 로그인에 application/json 이외의 요청 형식 사용 |
| 429 | RATE_LIMITED | 아래 로그인 시도 제한 초과 |

401 INVALID_CREDENTIALS는 원인과 관계없이 아래와 같은 코드·문구를 사용하고 fields=[]로 반환합니다. 존재하는 계정과 존재하지 않는 계정의 비밀번호 검증 시간 차이도 줄이도록 구현합니다.

```json
{
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "아이디 또는 비밀번호를 확인해 주세요.",
    "fields": [],
    "retry_after_ms": null
  },
  "request_id": "22222222-2222-4222-8222-222222222222"
}
```

400의 필드별 오류는 기존 FieldError의 field, code, message로 반환합니다. 예를 들어 password 누락은 field=password, code=required입니다. 본문 전체 오류는 fields=[]일 수 있습니다. 필드별 code의 우선순위는 v0.8.0에서 정리한 인증 API 공통 규칙([필드 오류 구성](#필드-오류-구성))과 같습니다. 429 이외의 위 오류는 retry_after_ms=null입니다.

- 아이디별로 최근 5분 안에 인증 실패가 5회 발생하면, 다섯 번째 실패 시점부터 5분 동안 다음 로그인을 429로 제한합니다. 등록 여부와 무관하게 입력한 아이디를 기준으로 같은 정책을 적용합니다. 제한 중인 요청은 차단 시간을 연장하지 않으며, 제한 해제 또는 로그인 성공 시 아이디별 실패 횟수를 초기화합니다.
- IP별로 최근 5분간 본문 크기 한도 내 로그인 요청을 최대 30회 허용합니다. v0.8.0부터 이 횟수는 서버 설정 LOGIN_MAX_REQUESTS_PER_IP로 조정하며 기본값은 30입니다([운영 설정과 한도](AUTH-IMPLEMENTATION.md#운영-설정과-한도)). IP에서 허용한 요청은 이후 형식 오류·성공·인증 실패·아이디 제한에 의한 429가 되더라도 집계하며, 한도를 넘는 요청부터 IP 제한으로 차단합니다. IP 제한으로 차단된 요청만 IP 허용 횟수에 추가하지 않고, 가장 오래된 허용 요청이 집계 구간에서 빠지면 다시 허용합니다.
- 본문 크기 확인 후 IP 제한 확인·집계를 입력 검증 결과 반환과 비밀번호 검증보다 먼저 수행합니다. IP 제한 중에는 JSON 문법·필드 오류나 미지원 콘텐츠 형식도 400·415 대신 429를 반환합니다. 이때 한도 내 정상 JSON에서 유효한 username을 확인할 수 있으면 아이디의 남은 차단 시간도 조회하되, 비밀번호 검증이나 아이디별 실패 횟수 변경은 하지 않습니다. IP에서 허용한 요청은 입력 검증, 아이디 제한 확인, 비밀번호 검증 순서로 처리합니다.
- 두 제한을 모두 적용하며, 429에는 실제 재시도까지 남은 양수 retry_after_ms와 이를 초 단위로 올림한 Retry-After 헤더를 반환합니다. 둘 다 제한 중이면 더 긴 대기 시간을 사용합니다.
- 제한 상태는 서버 프로세스들이 공유하는 저장소에서 원자적으로 관리합니다. 클라이언트가 임의로 지정한 전달 헤더를 IP로 신뢰하지 않습니다. IP는 [통신과 인증](#통신과-인증)의 클라이언트 IP 기준으로 정합니다.

### 로그인 앱 연동

앱은 로그인 성공 토큰을 서버 origin별 Keychain에 저장하고 비밀번호는 저장하지 않습니다. 이후 API와 인증 자산 요청에는 Bearer 헤더를 붙이며 다른 origin으로 토큰을 전달하지 않습니다. 재실행 시 /me/로 인증 상태를 확인하고, 서버 origin과 UserProfile UUID를 기준으로 기존 로컬 학습 기록을 연결합니다.

앱은 새 로그인·로그아웃·계정 삭제·계정 전환·서버 변경을 시작하거나 로그인을 취소할 때 인증 작업 세대를 갱신합니다. 요청은 당시 서버 origin과 인증 작업 세대를 보관하며, 로그인·로그아웃·/me/ 응답 및 보호 API의 401은 현재 origin과 세대가 일치할 때만 앱의 인증 상태에 반영합니다. 토큰 문자열이 같아도 이전 세대의 응답은 무시합니다. 이전 로그인 성공이 새 계정 상태를 덮어쓰거나, 늦은 로그아웃 204가 새 로그인 토큰을 지워서는 안 됩니다.

보호 API에서 401이면 해당 요청에 사용한 토큰이 현재 저장된 토큰과 같은지 확인한 후 토큰을 지우고 로그인 화면으로 이동합니다. 이전 요청의 늦은 401이 새 로그인 토큰을 지워서는 안 됩니다. 네트워크 오류·5xx는 인증 실패로 간주하지 않습니다. 인증 실패만으로 필기·미제출 답안을 삭제하지 않으며, 다른 계정의 기록을 표시하거나 그 계정으로 제출하지 않습니다. 재로그인 후 업로드·제출을 재시도할 때는 기존 Idempotency-Key와 client_answer_id를 유지합니다.

로그아웃은 서버에 폐기를 요청한 다음 기기의 토큰과 화면의 사용자 상태를 정리합니다. 서버 폐기를 확인하지 못한 채 로컬 로그아웃을 선택하면 서버 토큰이 남아 있을 수 있음을 안내합니다.

로그인에는 공통 API의 자동 재시도 정책을 적용하지 않습니다. 429·5xx·네트워크 오류 이후에는 사용자의 명시적 재시도로만 로그인 요청을 다시 전송하며, 429의 대기 시간이 지나기 전에는 재전송하지 않습니다. 응답이 유실되어 사용자가 재시도한 경우도 서버에는 별도 요청이므로, 실제 인증 실패가 발생했다면 각각 실패 횟수에 포함될 수 있습니다.

구현 및 회귀 검증 항목은 [AUTH-IMPLEMENTATION.md](AUTH-IMPLEMENTATION.md#v070-로그인-검증-항목-구현-완료)에 있습니다.

## v0.8.0 회원가입 계약

### 회원가입 범위와 공통 규칙

사용자가 아이디·표시 이름·학습 목표·비밀번호로 계정을 만들고 바로 로그인 상태가 되는 계약입니다. 현재 범위는 개발자가 운영하는 서버에 소수의 테스트 기기가 접속하는 MVP입니다. 이 범위에서 수용한 위험과 남용 대응 절차는 [AUTH-IMPLEMENTATION.md](AUTH-IMPLEMENTATION.md#운영-전제와-수용한-위험)에, 실제 서비스로 전환하기 전에 다시 정할 항목은 [AUTH-IMPLEMENTATION.md](AUTH-IMPLEMENTATION.md#서비스-전환-전에-다시-볼-항목)에 있습니다.

함께 추가하는 [계정 삭제](#v080-계정-삭제-계약)와 [AI 채점 사용량 상한](#ai-채점-사용량-상한-v080)은 각 절에서 정의합니다. 로그인·회원가입의 IP별 시도 제한은 [통신과 인증](#통신과-인증)의 클라이언트 IP 기준을 따릅니다.

개인정보와 계정 복구는 다음과 같이 다룹니다.

- 이메일, 실명, 학번, 전화번호, 생년월일 등 개인정보를 받지 않습니다. 아이디와 표시 이름에도 본인을 알 수 있는 정보를 쓰지 않도록 앱에서 안내합니다.
- 연락처를 받지 않으므로 비밀번호를 잊으면 계정을 복구할 수 없습니다. 관리자도 가입 계정의 소유자를 확인할 방법이 없으므로 가입 계정의 비밀번호를 재설정하지 않습니다. 비밀번호를 잊은 사용자는 새 계정을 만듭니다.
- 수업이 끝나면 관리자가 가입 계정과 학습 기록을 삭제할 수 있습니다.

아이디 중복 확인 전용 API, 이메일 인증, 초대 코드, 비밀번호 재설정·변경 API, 표시 이름 변경은 이번 범위에 포함하지 않습니다.

- 가입 기능은 서버 설정 SIGNUP_ENABLED로 켜고 끕니다. 꺼져 있으면 403 SIGNUP_DISABLED를 반환합니다. 가입 계정도 유료 AI 채점을 호출하므로, 서버는 AI 채점 사용량 상한을 설정하지 않은 상태에서 가입을 켤 수 없습니다. 조건은 [운영 설정과 한도](AUTH-IMPLEMENTATION.md#운영-설정과-한도)에서 정의합니다.
- 회원가입은 인증 없이 호출합니다. 로그인과 같이 이 엔드포인트에서 Bearer 인증을 수행하지 않으므로, 남아 있는 잘못된 Authorization 헤더가 가입을 차단하지 않습니다. 앱은 가입 요청에 해당 헤더를 보내지 않습니다.
- 요청·성공 응답은 application/json이며 성공 객체를 직접 반환합니다. 성공·오류 응답 모두 X-Request-ID와 Cache-Control: private, no-store를 포함합니다.
- 본문 크기 상한은 로그인과 같은 32 KiB(32768 bytes)이며, Content-Length 유무와 관계없이 JSON 파싱 전에 적용합니다. 초과하면 413 REQUEST_TOO_LARGE(fields=[])를 반환하고 가입 시도 횟수에 포함하지 않습니다.
- 비밀번호와 토큰은 URL·쿼리·로그·분석 이벤트에 기록하지 않습니다. 비밀번호는 해시로만 저장하고 응답하지 않습니다.
- Idempotency-Key가 필요하지 않으며, 기존 응시 API의 멱등성 영수증 저장 대상에도 포함하지 않습니다. 영수증에 발급 토큰을 저장하지 않기 위함입니다. 응답 유실은 아래 [회원가입 앱 연동](#회원가입-앱-연동)에서 처리합니다.

| 메서드 | 경로 | 인증 | 성공 | 동작 |
|---|---|---|---|---|
| GET | /api/v1/auth/signup-availability/ | 불필요 | 200 | 가입 가능 여부 반환 |
| POST | /api/v1/auth/signup/ | 불필요 | 201 | 계정·프로필·토큰 생성 후 로그인 응답과 같은 객체 반환 |

### 가입 가능 여부: GET /api/v1/auth/signup-availability/

앱이 가입 진입 버튼을 표시할지 정하기 위한 공개 API입니다. 인증 없이 호출하며 Bearer 인증을 수행하지 않습니다. 요청 본문을 받지 않고 로그인·가입 시도 제한에 포함하지 않습니다. 응답에는 X-Request-ID와 Cache-Control: private, no-store를 포함하며, 지원하지 않는 메서드는 405 METHOD_NOT_ALLOWED입니다.

성공 시 200과 아래 객체를 반환합니다. signup_enabled는 필수 boolean이며 요청 시점의 SIGNUP_ENABLED 값입니다. 이후 버전에서 필드가 추가될 수 있으므로 앱은 알 수 없는 필드를 무시합니다.

```json
{
  "signup_enabled": true
}
```

이 값은 안내용입니다. 조회 후 서버 설정이 바뀔 수 있으므로 가입 요청의 403 SIGNUP_DISABLED가 최종 판단입니다.

### 회원가입: POST /api/v1/auth/signup/

요청 본문은 아래 네 필드만 갖는 JSON 객체입니다. 문법이 깨진 JSON, 객체가 아닌 본문, 알 수 없는 필드, 누락·빈 문자열·잘못된 타입·규칙 위반은 400 VALIDATION_ERROR이며, fields는 [필드 오류 구성](#필드-오류-구성)을 따릅니다. 앱과 서버는 앞뒤 공백 제거, 대소문자 변환, 유니코드 정규화 등 입력값을 바꾸는 처리를 하지 않으며, 규칙에 맞지 않는 값은 고치지 않고 거절합니다.

| 필드 | 타입 | 필수 | 규칙 |
|---|---|---|---|
| username | string | 예 | 4~20자. 문자열 전체가 ^[a-z][a-z0-9_]{3,19}$와 일치해야 합니다. 영문 소문자로 시작하고 영문 소문자·숫자·_만 사용합니다. 부분 일치는 허용하지 않으며, 끝의 줄바꿈을 포함해 어떤 추가 문자도 허용하지 않습니다. |
| display_name | string | 예 | 1~20자(유니코드 코드 포인트 기준). 앞뒤에 공백(Unicode White_Space 속성 문자)을 둘 수 없습니다. 제어 문자(Cc), 줄·문단 구분자(Zl·Zp), 양방향 제어 문자(Unicode Bidi_Control 속성)를 포함할 수 없습니다. 다른 사용자와 중복될 수 있습니다. |
| learning_goal | string | 예 | arts_school_entrance, arts_school_student, college_entrance, teacher_exam, other 중 하나입니다. UserProfile.learning_goal과 같은 목록입니다. |
| password | string | 예 | 1~1024자이며 서버의 비밀번호 정책을 통과해야 합니다. |

```json
{
  "username": "student01",
  "display_name": "청음 연습생",
  "learning_goal": "college_entrance",
  "password": "example-password"
}
```

표시 이름의 길이·문자 규칙은 가입 요청에만 적용합니다. 관리자가 만든 기존 계정의 display_name은 최대 80자일 수 있으므로, 앱은 로그인·/me/ 응답의 display_name이 20자 이하라고 가정하지 않습니다. 표시 이름은 가입 후 바꿀 수 없으므로, 실명 등을 잘못 입력했다면 계정을 삭제하고 다시 가입합니다.

learning_goal은 가입 화면에서 사용자가 직접 고른 값이며, 가입 후 기존 PATCH /me/로 바꿀 수 있습니다. 서버가 기본값으로 채우지 않으므로 가입 계정의 other는 사용자가 "기타"를 고른 경우입니다.

로그인은 대소문자를 구분하고 입력값을 바꾸지 않습니다. 가입 아이디를 소문자로 제한하고 앱의 아이디 입력란에서 자동 대문자를 끄므로, iPad 키보드의 자동 대문자 때문에 가입한 아이디와 로그인할 때 입력한 아이디가 달라지는 문제를 막습니다. 관리자가 만든 기존 계정은 이 형식 규칙을 따르지 않아도 되며, 로그인 username 규칙(1~150자)은 바꾸지 않습니다.

아이디 중복은 대소문자를 구분하지 않고 관리자가 만든 계정을 포함한 모든 계정과 비교합니다. 예를 들어 관리자가 만든 Student01이 있으면 student01로 가입할 수 없습니다. 서버는 가입 외의 계정 생성·아이디 변경 경로에서도 대소문자만 다른 아이디를 허용하지 않습니다. 같은 아이디로 동시에 가입하면 하나만 201이고 나머지는 409입니다.

비밀번호 정책은 현재 서버 설정상 최소 8자, 흔한 비밀번호 금지, 숫자로만 된 비밀번호 금지, 아이디와 유사한 비밀번호 금지입니다. username이 형식 규칙을 통과한 경우에만 아이디 유사성까지 검사합니다. 정책은 가입 시에만 적용하며 로그인 검증에는 다시 적용하지 않습니다. 비밀번호 확인 입력은 앱 화면에서만 비교하고 서버로 보내지 않습니다.

성공 시 201과 로그인 성공과 같은 스키마의 객체를 반환합니다. 모든 필드는 필수이며 token_type은 항상 Bearer입니다. user.learning_goal은 요청한 값입니다. 기존 201 응답과 같이 생성된 리소스의 절대 URL을 Location 헤더로 반환합니다. 가입으로 만든 프로필은 발급한 토큰으로 조회하는 /api/v1/me/이므로 값은 https://<공개 호스트>/api/v1/me/처럼 [통신과 인증](#통신과-인증)의 공개 origin 규칙을 따릅니다.

```json
{
  "access_token": "<발급된 토큰>",
  "token_type": "Bearer",
  "user": {
    "id": "11111111-1111-4111-8111-111111111111",
    "display_name": "청음 연습생",
    "learning_goal": "college_entrance"
  }
}
```

가입 결과는 다음을 보장합니다.

- 201이면 계정·프로필·토큰이 모두 생성되어 있고, 오류 응답이면 아무것도 생성하지 않습니다.
- 생성된 계정은 사용 가능한 비밀번호를 가진 활성 계정이며 관리자 권한이 없습니다.
- 토큰 수명·폐기·재로그인은 [토큰 수명과 폐기](#토큰-수명과-폐기)를 그대로 따릅니다.
- 가입 전에 같은 아이디로 발생한 로그인 실패 기록과 차단 상태는 가입 성공 시 초기화되므로 새 계정의 로그인을 막지 않습니다.
- 회원가입 요청은 로그인 시도 제한의 아이디별·IP별 집계에 포함하지 않습니다.

서버 내부의 처리 순서와 잠금 방식은 [AUTH-IMPLEMENTATION.md](AUTH-IMPLEMENTATION.md#회원가입-처리)에 있습니다.

### 오류와 가입 시도 제한

오류는 기존 error(code, message, fields, retry_after_ms), request_id 형식을 사용합니다. 앱은 message 문구가 아니라 HTTP 상태, error.code, FieldError의 code로 분기합니다. 429 이외의 오류는 retry_after_ms=null입니다.

| HTTP | error.code | 조건 |
|---|---|---|
| 400 | VALIDATION_ERROR | JSON 문법·필드·타입·길이·형식 규칙 또는 비밀번호 정책 위반 |
| 403 | SIGNUP_DISABLED | 가입 기능이 꺼져 있음 |
| 405 | METHOD_NOT_ALLOWED | 지원하지 않는 메서드 |
| 409 | USERNAME_TAKEN | 대소문자 무시 기준으로 이미 사용 중인 아이디 |
| 413 | REQUEST_TOO_LARGE | 본문이 32 KiB 초과 |
| 415 | UNSUPPORTED_MEDIA_TYPE | application/json 이외의 요청 형식 |
| 429 | RATE_LIMITED | 아래 가입 시도 제한 초과 |

#### 필드 오류 구성

- 문법이 깨진 JSON, JSON 객체가 아닌 본문(배열·null·숫자 등), 알 수 없는 필드를 포함한 객체는 다른 필드를 검사하지 않고 fields=[]인 400을 반환합니다.
- 그 외에는 위반한 모든 필드를 한 번에 반환합니다. 필드마다 아래 순서에서 처음 해당하는 code 하나만 사용합니다.
- password가 아래 1~5를 통과한 경우에만 비밀번호 정책을 검사합니다. 위반한 정책마다 field=password인 FieldError를 하나씩 서버 비밀번호 정책의 순서대로 반환합니다. 따라서 password만 같은 field의 FieldError가 여러 개일 수 있으며, 앱은 이를 가정합니다.
- 400과 409가 모두 해당하면 400을 반환하며, 중복 확인은 모든 필드가 유효할 때만 수행합니다. 따라서 약한 비밀번호와 이미 사용 중인 아이디를 함께 보내면 먼저 400을 받고, 비밀번호를 고쳐 다시 보내면 409를 받습니다. 의도된 동작입니다.
- 이 우선순위는 인증 API의 공통 규칙입니다. 로그인(username·password)도 같은 순서를 사용하며, 해당 API의 필드에 없는 규칙(min_length, invalid_format, invalid_choice, 비밀번호 정책)은 적용하지 않습니다. 최대 길이는 각 API의 필드 규칙을 따릅니다.

| 순서 | code | 대상 field | 조건 |
|---:|---|---|---|
| 1 | required | 전체 | 누락 |
| 2 | invalid | 전체 | 문자열이 아님 |
| 3 | blank | 전체 | 빈 문자열 |
| 4 | max_length | username, display_name, password | 최대 길이 초과(username 20, display_name 20, password 1024) |
| 5 | invalid | username, display_name, password | 짝이 맞지 않는 서로게이트 등 UTF-8로 인코딩할 수 없는 문자열 |
| 6 | min_length | username | 4자 미만 |
| 7 | invalid_format | username, display_name | 허용하지 않는 문자 또는 형식 |
| 8 | invalid_choice | learning_goal | 허용 목록에 없는 값 |

| field | code | 조건 |
|---|---|---|
| password | password_too_short / password_too_common / password_entirely_numeric / password_too_similar | 서버 비밀번호 정책 위반 |

예를 들어 username "Ab"는 min_length 하나, "1abc"와 "student01\n"은 invalid_format입니다. password "1234"는 password_too_short, password_too_common, password_entirely_numeric 세 개를 반환합니다. 1025자이면서 짝이 맞지 않는 서로게이트를 포함한 password는 max_length입니다.

409 USERNAME_TAKEN은 fields=[{"field": "username", "code": "taken", ...}]로 반환합니다. 로그인은 원인과 관계없이 같은 오류를 반환해 계정 존재 여부를 숨기지만, 가입은 아이디의 존재 여부를 알려줄 수밖에 없습니다. 가입을 켜면 로그인의 존재 여부 숨김이 완전하지 않다는 점을 수용하고, 아래 IP 제한으로 대량 확인을 막습니다.

```json
{
  "error": {
    "code": "USERNAME_TAKEN",
    "message": "이미 사용 중인 아이디입니다.",
    "fields": [
      {"field": "username", "code": "taken", "message": "이미 사용 중인 아이디입니다."}
    ],
    "retry_after_ms": null
  },
  "request_id": "22222222-2222-4222-8222-222222222222"
}
```

#### 가입 시도 제한

- IP별로 최근 5분간 본문 크기 한도 내 가입 요청을 서버 설정 SIGNUP_MAX_REQUESTS_PER_IP회까지 허용합니다. 집계 방식은 로그인 IP 제한과 같으며 로그인과 별도로 집계합니다. 허용한 요청은 이후 400·409·415·성공이 되거나 아래 성공 한도로 429가 되더라도 집계합니다. 요청 제한으로 차단된 요청만 요청 횟수에 추가하지 않습니다.
- IP별로 최근 24시간 가입 성공을 서버 설정 SIGNUP_MAX_SUCCESSES_PER_IP회까지 허용합니다. 한도에 도달하면 집계 수가 한도 아래로 내려갈 때까지 이후 가입 요청을 429로 제한합니다. 같은 IP의 동시 요청도 한도를 넘어 계정을 생성하지 않으며, 이 경우 입력 검증을 통과한 요청도 429가 될 수 있습니다.
- 응답 판정 순서는 413, 403, IP 요청 제한 429, IP 가입 성공 한도 429, 415, 400, 409, 201입니다. 403과 413으로 거절한 요청은 IP 요청 횟수에 포함하지 않습니다. 따라서 IP 제한 중에는 400·409·415 대신 429를 반환합니다.
- 429에는 실제 재시도까지 남은 양수 retry_after_ms와 이를 초 단위로 올림한 Retry-After 헤더를 반환합니다. 두 제한이 겹치면 더 긴 대기 시간을 사용하며, 요청 제한으로 차단할 때도 성공 한도의 남은 시간을 함께 고려합니다.
- 한도 값과 기본값은 서버 설정이며 [운영 설정과 한도](AUTH-IMPLEMENTATION.md#운영-설정과-한도)에서 정의합니다. 앱은 한도 값을 가정하지 않고 retry_after_ms와 Retry-After만 사용합니다.
- 학교 Wi-Fi처럼 여러 사용자가 같은 공인 IP를 공유하면 그 사용자 전체가 하나의 IP 한도를 함께 씁니다. 배포 테스트에서 서버가 네트워크별로 다른 IP를 보는지 확인하고, 같은 IP를 쓰는 사용자가 많으면 인원에 맞게 한도를 조정합니다([배포 테스트](AUTH-IMPLEMENTATION.md#배포-테스트)). 특정 IP 대역을 제한에서 제외하는 허용 목록은 두지 않습니다.

### 회원가입 앱 연동

앱은 201 응답을 로그인 성공과 같이 처리합니다. 토큰을 서버 origin별 Keychain에 저장하고 비밀번호는 저장하지 않으며, 응답의 UserProfile UUID로 로컬 학습 기록을 연결합니다. 가입 시작·취소도 인증 작업 세대를 갱신하며, 이전 세대의 가입 성공은 현재 인증 상태에 반영하지 않습니다.

- 로그인 화면을 표시하거나 서버 origin이 바뀌면 GET /auth/signup-availability/를 조회합니다. signup_enabled=false이면 가입 진입 버튼을 숨기고, 네트워크 오류·5xx로 조회하지 못하면 버튼을 표시합니다.
- 가입 화면은 아이디, 표시 이름, 학습 목표, 비밀번호, 비밀번호 확인을 입력받습니다. 학습 목표는 기본값 없이 사용자가 고르게 합니다.
- username 입력란은 자동 대문자와 자동 수정을 끄고, 소문자 형식을 미리 안내합니다.
- 아이디와 표시 이름에 실명, 학번, 전화번호 등 본인을 알 수 있는 정보를 쓰지 말라고 안내합니다. 표시 이름에는 닉네임을 쓰도록 안내하고, 가입 후 바꿀 수 없다는 점도 함께 알립니다.
- 비밀번호 입력란 근처에 비밀번호를 잊으면 복구할 수 없다는 안내를 항상 표시합니다. 비밀번호 입력란은 새 비밀번호 입력란으로 지정해 기기의 비밀번호 관리자를 사용할 수 있게 합니다.
- 앱의 입력 검증은 안내용이며 최종 판단은 서버가 합니다. username은 문자열 전체 일치로, display_name 길이는 유니코드 코드 포인트 수로 확인합니다.
- 회원가입에는 공통 API의 자동 재시도 정책을 적용하지 않습니다. 429·5xx·네트워크 오류 이후에는 사용자의 명시적 재시도로만 다시 전송하며, 429의 대기 시간이 지나기 전에는 재전송하지 않습니다.
- 응답 유실 후 같은 아이디로 재시도해 409를 받으면, 직전 가입이 성공했을 수 있다고 안내하고 아이디를 채운 로그인 화면으로 이동합니다. 로그인을 자동으로 시도하지 않습니다.
- 응답 유실 후 재시도해 429를 받은 경우에도 직전 가입이 성공해 성공 한도를 채웠을 수 있습니다. 앱은 대기 시간과 함께 같은 아이디로 로그인을 먼저 시도해 보라고 안내합니다.
- 403 SIGNUP_DISABLED이면 가입이 현재 제공되지 않는다고 안내하고 로그인 화면으로 돌아가며, 가입 진입 버튼을 숨깁니다.

구현 및 회귀 검증 항목은 [AUTH-IMPLEMENTATION.md](AUTH-IMPLEMENTATION.md#v080-검증-항목)에 있습니다.

## v0.8.0 계정 삭제 계약

### 계정 삭제 범위와 공통 규칙

로그인한 사용자가 앱 안에서 자기 계정과 학습 기록을 영구 삭제하는 계약입니다. 앱 안에서 계정을 만들 수 있으므로 앱 안에서 삭제할 수도 있어야 합니다. App Store 심사 지침 5.1.1(v)도 앱 내 계정 생성을 지원하는 앱에 앱 내 계정 삭제를 요구합니다. 가입 계정과 관리자가 만든 계정 모두 사용할 수 있으며, SIGNUP_ENABLED와 관계없이 항상 제공합니다. 삭제는 되돌릴 수 없고 유예 기간이나 비활성화 단계를 두지 않습니다.

비밀번호를 다시 묻지 않습니다. 실수로 인한 삭제는 앱의 확인 창으로 막고, 서버는 유효한 토큰을 사용자의 삭제 요청으로 처리합니다. 이 판단의 위험은 [AUTH-IMPLEMENTATION.md](AUTH-IMPLEMENTATION.md#운영-전제와-수용한-위험)에 있습니다.

| 메서드 | 경로 | 인증 | 성공 | 동작 |
|---|---|---|---|---|
| DELETE | /api/v1/me/ | Bearer | 204 | 계정과 학습 기록 영구 삭제, 응답 본문 없음 |

- Authorization: Bearer <access_token>이 필요합니다. 토큰 누락·무효·폐기는 401 AUTHENTICATION_REQUIRED입니다.
- 요청 본문이 없습니다. 본문을 보내도 읽거나 검증하지 않으므로 Content-Type과 본문 형식 때문에 거절하지 않습니다. 모든 /api/v1/ 요청에 적용되는 11 MiB 상한의 413은 예외입니다.
- Idempotency-Key가 필요하지 않으며 멱등성 영수증 저장 대상이 아닙니다.
- 성공 시 204이며 본문이 없습니다. 성공·오류 응답 모두 X-Request-ID와 Cache-Control: private, no-store를 포함합니다.

### 계정 삭제: DELETE /api/v1/me/

관리자 권한(is_staff 또는 is_superuser)이 있는 계정은 403 ACCOUNT_DELETION_NOT_ALLOWED를 반환합니다. 관리자 계정을 앱에서 실수로 삭제하지 않게 하기 위함이며, 필요하면 관리 명령으로 삭제합니다.

응답 판정 순서는 401, 403, 204입니다.

| HTTP | error.code | 조건 |
|---|---|---|
| 401 | AUTHENTICATION_REQUIRED | 토큰 누락·무효·폐기 |
| 403 | ACCOUNT_DELETION_NOT_ALLOWED | 관리자 권한이 있는 계정 |
| 405 | METHOD_NOT_ALLOWED | /me/가 지원하지 않는 메서드 |

삭제 결과는 다음을 보장합니다.

- 204이면 계정, 프로필, 토큰, 모든 응시·답안·채점 작업·자기채점 이력·멱등성 영수증, 해당 아이디의 로그인 실패 기록이 삭제되어 있습니다. 일부만 삭제된 상태는 남기지 않습니다.
- AI 채점 사용량 기록은 사용자와의 연결만 끊고 남기므로, 삭제한 사용자의 사용량도 서버 전체 상한 집계에 남습니다([AI 채점 사용량 상한](#ai-채점-사용량-상한-v080)).
- 답안 이미지 파일은 삭제가 확정된 후 저장소에서 지웁니다. 파일 삭제 실패는 204 응답을 바꾸지 않으며, 서버가 기록을 남겨 관리자가 정리합니다.
- 삭제 확정 이후 이전 토큰으로 보낸 요청은 401입니다. 삭제와 겹쳐 처리 중이던 같은 사용자의 요청도 삭제 확정 후 그 사용자의 데이터를 남겨서는 안 됩니다. 이런 요청이 삭제된 사용자의 데이터를 쓰려다 실패하면 500이 아닌 401 AUTHENTICATION_REQUIRED를 반환합니다.
- 진행 중인 채점 작업도 함께 삭제하며, 그 결과는 저장하지 않습니다. 이미 시작한 AI 호출은 취소되지 않을 수 있으며, 그 사용량은 보존한 사용량 기록에 남습니다.
- 삭제한 아이디는 즉시 다시 가입할 수 있습니다. 새 계정은 새 UserProfile UUID를 받으며 이전 기록은 복구하지 않습니다. IP별 가입 성공 집계는 계정 삭제로 줄어들지 않습니다.

비밀번호를 잊어 로그인할 수 없는 계정은 수업 종료 후 관리자가 정리할 때 함께 삭제합니다. 서버 내부 삭제 절차와 관리자용 삭제 명령은 [AUTH-IMPLEMENTATION.md](AUTH-IMPLEMENTATION.md#계정-삭제-절차)에 있습니다.

### 계정 삭제 앱 연동

- 연결 설정 화면에서 진입합니다. 확인 창에서 표시 이름과 함께 계정, 서버의 응시·답안·채점 결과, 이 기기에 있는 해당 계정의 로컬 학습 기록·필기·미제출 답안이 영구 삭제되며 되돌릴 수 없다고 안내하고, 사용자가 삭제를 고른 경우에만 요청합니다. 앱은 아이디를 보관하지 않으므로 표시 이름으로 계정을 구분합니다.
- 요청 전에 진행 중인 업로드·제출·결과 조회를 취소하고 인증 작업 세대를 갱신합니다. 이전 세대의 삭제 응답은 현재 인증 상태에 반영하지 않습니다.
- 204이면 Keychain의 토큰과, 현재 서버 origin과 UserProfile UUID에 연결된 로컬 학습 기록·필기·미제출 답안을 삭제하고 로그인 화면으로 이동합니다. 앱은 204를 JSON 본문 디코딩이나 Content-Type 검사 없이 성공으로 처리합니다. 로컬 기록 삭제에 실패해도 계정은 이미 삭제되었으므로 로그인 화면으로 이동하고 그 사실을 안내합니다.
- 403 ACCOUNT_DELETION_NOT_ALLOWED이면 토큰과 로컬 기록을 유지하고 관리자 계정은 앱에서 삭제할 수 없다고 안내합니다.
- 계정 삭제에는 공통 API의 자동 재시도 정책을 적용하지 않습니다. 5xx·네트워크 오류 이후에는 토큰과 로컬 기록을 유지하고 삭제 여부를 확인하지 못했다고 안내하며, 사용자의 명시적 재시도로만 다시 전송합니다. 해석할 수 없는 응답(프록시의 HTML 403 등)도 같게 처리합니다.
- 삭제 요청이 401을 받으면 저장된 토큰을 지우고 로그인 화면으로 이동합니다. 토큰은 기기 간에 공유되므로 이 401은 응답을 잃어버린 이전 삭제와 다른 기기의 로그아웃을 구별하지 못합니다. 앱은 계정이 이미 삭제됐거나 다른 기기에서 로그아웃했을 수 있다고 안내하고, 같은 아이디로 다시 로그인되면 계정이 남아 있다는 점을 알립니다. 로컬 기록은 유지합니다.

## 문제와 악보

준비된 3문제는 각각 6/8, 4/4, 3/4의 높은음자리표 단선율 8마디입니다. 기존 정답 XML의 음정·길이·부점·임시표·쉼표·붙임줄·셋잇단음표를 보존합니다. XML의 인쇄용 메타데이터와 DTD를 제거하고, 원본 표기 템포 96(4분음표 기준)과 C Major 메타데이터를 명시한 MXL을 제공합니다.

새 악보 프로파일은 sori-monophonic-v2입니다. 기존 v1에 3/4·6/8, 16분음표, 3:2 셋잇단음표, 빔 표기를 추가합니다. 임의의 MusicXML 전체를 지원한다는 뜻은 아닙니다. 프론트는 예전 v1 fixture도 계속 읽습니다.

MXL은 정확히 mimetype, META-INF/container.xml, score.xml 세 엔트리를 갖습니다. 압축 1 MiB, 해제 합계 4 MiB 한도입니다. main 8마디, scale 2마디 또는 3마디, part_id=P1, MusicXML 4.0입니다. 크기와 SHA-256을 검사합니다.

문제 버전과 파일 bytes는 불변입니다. 응시 생성 시 문제와 재생 계획의 스냅샷을 고정합니다. 정답 main MXL은 로컬 합성 재생을 위해 제출 전 내려받지만, 앱은 제출 후에만 악보를 표시합니다. 정답을 기기에 전달하지 않는 감독형 시험 구조가 아닙니다.

## 답안 이미지

- 논리 캔버스 1330 × 846, 출력 2배, PNG 2660 × 1692입니다.
- 8비트 RGB 또는 완전히 불투명한 RGBA, 흰 배경과 검은 필기입니다.

| POST | /attempts/{id}/start/ | 200 | 자산·피아노 준비 후 시작, 본문 없음 |
| POST | /attempts/{id}/answers/ | 201 | multipart PNG 업로드 |
| GET | /attempts/{id}/answers/{answer_id}/image/ | 200 | 업로드한 원본 PNG |
| POST | /attempts/{id}/submit/ | 200 / 202 | Practice 자기채점 시작 / Exam AI 작업 생성 |
| GET | /attempts/{id}/result/ | 200 | Practice 최신 자기채점 / Exam 채점 진행·결과 |
| PUT | /attempts/{id}/self-assessment/ | 200 | Practice 전체 마디 오류·완료 상태 저장 |
| POST | /attempts/{id}/grading-retries/ | 202 | Exam의 실패한 같은 답안 재시도, 본문 없음 |

공개 오선은 /assets/sheets/{layout_id}.png에서 제공합니다. 기존 /api/health/도 유지합니다.

## 응시·제출·재전송

응시 상태는 ready → in_progress → submitted입니다. 시작 반복 호출은 타이머를 초기화하지 않습니다. 권장 시간은 아래 전체 재생·필기 시간표로 계산하며, 초과해도 제출할 수 있습니다. 기존 응시는 생성 당시의 계획과 시간을 유지합니다.

업로드와 제출은 별개입니다. multipart 필드는 image, client_answer_id, answer_format_version(텍스트 1), sheet_layout_id입니다. 서버는 실제 PNG와 규격을 검사하고 원본 bytes·해시를 저장합니다.

생성·업로드·제출·자기채점 저장·재시도에는 Idempotency-Key(UUID)를 보냅니다. 같은 사용자·경로·키·본문을 재전송하면 최초 영수증을 반환합니다. 같은 키의 다른 본문은 409 IDEMPOTENCY_KEY_REUSED, 진행 중인 동일 요청은 409 REQUEST_IN_PROGRESS입니다.

(attempt, client_answer_id)는 유일합니다. 동일 이미지·ID의 업로드 영수증은 제출 후에도 재조회할 수 있습니다. 제출은 answer_id를 고정하며 마지막 업로드를 임의 선택하지 않습니다. 같은 답안 재제출은 새 채점 작업을 만들지 않습니다. 다른 답안으로 바꾸는 요청은 409입니다.

최종 제출·선택 답안과 Practice 초기 자기채점 또는 Exam 채점 작업을 하나의 DB 트랜잭션에 저장합니다. Exam은 별도 워커가 DB의 작업을 가져가므로 HTTP 프로세스 재시작이나 앱 화면 이탈로 작업을 잃지 않습니다. 파일 저장이 성공한 다음 업로드 성공을 반환합니다.


## v3/v4의 공통 재생 시간표

새 응시의 playback_plan.version은 4입니다. 기존 저장 응시의 version=2/3은 변경하지 않습니다.

1. 시작 후 2초 대기 → 스케일 재생
2. 스케일 종료 후 2초 대기 → 예비박 1마디 → 첫 1–8마디 전체 재생
3. 필기 20초 → 1–2 → 20초 → 1–2 → 20초 → 1–4 → 20초 → 3–4 → 20초 → 3–6 → 20초 → 5–6 → 20초 → 5–8 → 20초 → 7–8 → 20초 → 7–8
4. 필기 20초 → 예비박 1마디 → 마지막 1–8마디 전체 재생 → 마지막 필기 120초

예비박은 처음과 마지막 전체 재생 앞에만 있으며, 첫 박을 크게 냅니다. 4/4는 4번, 3/4는 3번, 6/8은 8분음표 간격으로 6번 클릭합니다. 6/8을 두 번의 점4분음표 클릭으로 바꾸지 않습니다.
예비박 마지막 클릭 이후 한 박 간격이 지나면 문제의 첫 박입니다. 클릭과 문제는 하나의 MIDI 시퀀스에서 재생하므로 중간에 로딩·별도 휴지가 없습니다.

initial_delay_ms=2000, pause_after_scale_ms=2000, count_in.before_step_orders=[1,11]입니다.
count_in에는 measures=1, beats_per_measure/beat_unit=문제 박자표, accent_velocity=110, velocity=70, profile_id=sori-click-v1을 보냅니다.
steps의 pause_after_ms는 1~10번째 20000, 마지막 120000입니다. 기존 release_tail_ms=300은 이 휴지 시간에 포함하며 별도로 더하지 않습니다.

현재 4분음표 BPM 96에서 전체 길이는 4/4 문제 434초, 3/4·6/8 문제 406.5초입니다. recommended_duration_seconds는 각각 434, 407로 올림합니다.
문제 자산과 저장된 문제 버전의 bytes·해시는 그대로 유지하며, 현재 목록·상세 안내와 새 응시 스냅샷의 권장 시간을 계산해서 제공합니다.

필기 대기 중 일시정지는 남은 시간을 저장해 이어집니다. 재생 도중 일시정지는 현재 구간 처음부터 재개하며, 전체 재생이면 예비박도 다시 제공합니다.
최종 2분이 지나면 제출 안내를 표시합니다. 현재 연습의 advisory 정책대로 자동 제출·자동 편집 잠금은 하지 않습니다.

## AI 평가

- grading_mode=automatic, grading_version=ai-melodic-v1입니다. 점수·음정/리듬 평가는 학습 참고용 AI 추정값이며 기존 50:50 편집 거리 산식과 다릅니다.
- AI 호출 한 번으로 보이는 필기의 MusicXML, 점수, 마디별 오류, 다정한 한국어 피드백을 요청합니다. 정답에 맞춰 필기 내용을 보정하지 않도록 지시합니다.
- 모델과 reasoning effort는 서버 설정이며 작업 생성 시 고정합니다. 기본 설정은 기존 실험의 openai/gpt-6.1-sol, medium입니다.
- 프롬프트 원문·버전, 모델·설정, 응답, 사용량과 provider 요청 ID를 작업에 보관합니다. 키는 앱·응답·로그에 포함하지 않습니다.
- 서버가 JSON 구조·점수 범위·마디 번호를 검증합니다. 문법 검증이 음악적 정확도를 보장하지는 않습니다.
- 좌표는 AI가 추측하지 않습니다. 초기 주석은 서버의 고정 마디 영역에 표시합니다. 위치가 불명확하면 measure와 bbox는 null입니다.

| status | 점수 | 의미 |
|---|---|---|
| queued | null | 저장·대기 |
| processing | null | AI 요청 처리 |
| completed | 숫자, 0도 유효 | AI 평가 완료 |
| needs_review | null | 필기를 확실히 평가하기 어려움 |
| failed | null | 연결·시간 초과·응답 검증 실패 |

AI가 한 번에 처리하므로 진행 중 stage=recognizing으로 표시하고 완료 시 done으로 바꿉니다. 내부의 세부 진행 단계를 추정해서 표시하지 않습니다. needs_review도 recognizing입니다.

대기 중 2초 간격으로 결과를 조회합니다. 60초 이후에는 화면을 나갔다 나중에 돌아올 수 있습니다. 앱을 닫아도 서버 작업은 계속됩니다. 초기 서버 제한은 240초이며 별도 HTTP 자식 프로세스를 종료해 강제 적용합니다. 작업 lease 만료도 failed로 복구합니다.

실패하고 retryable=true일 때 같은 답안으로 새 job_id를 발급합니다. 오래된 작업의 늦은 응답이 새 결과를 덮어쓰지 않습니다. 초기 설정은 응시당 최대 3개 작업이며 서버 설정으로 조정합니다. v0.8.0부터 이와 별도로 사용자별·서버 전체의 [AI 채점 사용량 상한](#ai-채점-사용량-상한-v080)을 적용합니다. 네트워크 결과가 불명확한 AI 요청을 서버가 자동 반복해 과금하지 않습니다. 재시도는 명시적 요청입니다.

### AI 채점 사용량 상한 (v0.8.0)

응시당 작업 수 제한과 별도로, 서버는 유료 AI 호출 총량을 사용자별·서버 전체의 최근 24시간 채점 작업 수로 제한합니다. 가입 계정과 관리자가 만든 계정 모두에 적용합니다. 상한 값은 서버 설정 AI_MAX_JOBS_PER_USER_PER_DAY, AI_MAX_JOBS_PER_DAY이며 [운영 설정과 한도](AUTH-IMPLEMENTATION.md#운영-설정과-한도)에서 정합니다. 앱은 상한 값을 가정하지 않습니다.

- POST /attempts/{id}/submit/과 POST /attempts/{id}/grading-retries/가 새 채점 작업을 만들 때만 확인합니다. 기존 검증을 모두 통과한 뒤 확인하며, 같은 답안 재제출처럼 새 작업을 만들지 않는 요청은 제한하지 않습니다.
- 실패한 작업도 이미 AI를 호출했을 수 있으므로 집계에 포함합니다. 계정을 삭제해도 그 사용자의 작업은 서버 전체 집계에 남으므로, 가입과 삭제를 반복해 서버 전체 상한을 우회할 수 없습니다. 사용자별 상한은 계정 단위이므로 새 계정은 새 한도로 시작합니다. 비용의 최종 상한은 서버 전체 상한이 보장합니다.
- 동시 요청도 상한을 넘어 작업을 만들지 않습니다.
- 상한에 도달하면 429 GRADING_QUOTA_EXCEEDED를 반환하고 제출·작업을 저장하지 않습니다. retry_after_ms는 집계 수가 상한 아래로 내려가 새 작업을 만들 수 있을 때까지 남은 양수 시간이며, 이를 초 단위로 올림한 Retry-After 헤더를 함께 반환합니다. 두 상한이 모두 해당하면 더 긴 시간을 사용합니다.
- 오류 응답은 멱등성 영수증에 저장하지 않습니다. 앱은 대기 시간이 지난 뒤 같은 Idempotency-Key와 본문으로 다시 요청할 수 있으며, 업로드한 답안과 기기의 필기는 그대로 유지합니다.
- 앱은 GRADING_QUOTA_EXCEEDED에 공통 API의 자동 재시도 정책을 적용하지 않습니다. 이 판단은 HTTP 상태가 아니라 error.code로 합니다. 채점 사용량 한도에 도달했다고 안내하고 남은 대기 시간을 표시하며, 대기 시간이 지난 뒤 사용자의 명시적 요청으로만 같은 Idempotency-Key로 다시 보냅니다.
- 이와 별도로 앱의 공통 자동 재시도는 error.code와 관계없이 대기 시간(Retry-After 또는 retry_after_ms)이 30초를 넘는 429를 자동 재시도하지 않고 호출자에게 오류로 반환합니다.

```json
{
  "error": {
    "code": "GRADING_QUOTA_EXCEEDED",
    "message": "AI 채점 사용량 한도에 도달했습니다. 잠시 후 다시 시도해 주세요.",
    "fields": [],
    "retry_after_ms": 3600000
  },
  "request_id": "22222222-2222-4222-8222-222222222222"
}
```

## 오류와 검증

오류 객체는 error(code, message, fields, retry_after_ms), request_id입니다. HTTP 요청 실패와 채점 작업 실패를 구분합니다. 결과를 정상 조회해 failed를 받는 것은 HTTP 200입니다.

원본 v0.2.0 examples는 구버전 클라이언트 회귀 검증용으로 유지합니다. 이번 세 문제의 실제 예시는 question-excerpt-1.json부터 question-excerpt-3.json, questions-v0.4.json 및 attempt-ready-v3.json입니다. 실제 구현·검증 범위는 ../VALIDATION.md를 확인합니다.
