# SORI MXL 전달·iPad 합성 재생 평가 및 구현 계약

개정: 2026-10-23 · API 계약 0.2.0

## 1. 평가 결과와 사용자 확인 사항

**현재 범위에는 채택할 만한 방식이다.** 사용자는 개인 연습용이라 기기에 정답 데이터가 존재해도 괜찮고, 일정한 템포의 피아노 합성음이면 충분하다고 확인했다. 이 조건에서는 문제 원본 하나를 표시·재생·채점의 공통 기반으로 쓰는 이점이 있다.

다만 최초 완성까지 가장 단순한 방법은 녹음 파일 재생이다. MXL로 바꾸면 iPad 담당자에게 악보 파싱·렌더링·MIDI 변환·합성·마디 경계 처리라는 추가 개발이 생긴다. 전송량 감소만으로 결정할 문제는 아니며, 작은 악보보다 앱 번들 악기 음원의 크기가 더 클 수도 있다. 데이터와 재생을 구조화해 장기적으로 템포 조절·구간 연습·정답 악보 표시를 확장하려는 방향에 더 적합하다.

| 관점 | 구간별 녹음 파일 | MXL + iPad 합성 | SORI 판단 |
|---|---|---|---|
| 처음 구현할 프론트 작업량 | 작음 | 큼 | 프론트 일정에 악보 엔진 검증을 별도 반영 |
| 서버 출제·보관 | 구간 음원 제작·배포 필요 | MXL과 구간 계획 관리 | 문제 수가 늘면 MXL 관리 이점 |
| 문제당 네트워크 | 녹음 길이·품질에 비례 | 작은 악보가 중심 | 단선율 짧은 문제에 유리할 가능성 |
| 음색·실제 연주 표현 | 녹음 그대로 재생 | 합성 엔진·음원·지원 기호에 의존 | 피아노 합성음이면 충분하므로 허용 |
| 템포·구간 변경 | 새 파일 또는 오디오 처리 | 이벤트·재생 계획 변경 | 이후 연습 기능에 유리 |
| 표시와 재생의 일관성 | 악보와 음원을 별도 관리 | 같은 MXL에서 파생 | 불일치를 줄일 수 있음. 변환 검증은 필요 |
| 정답 데이터 은닉 | 기기에 악보 기호는 안 줘도 됨 | 기기에 정확한 음표·리듬 전달 | 개인 연습용이므로 수용 |
| 오프라인 재생 | 다운로드 후 가능 | MXL·악기·엔진 준비 후 가능 | 양쪽 모두 가능. 서버 채점은 온라인 필요 |
| 디바이스 차이 | 디코더·출력 차이 | 엔진·음원·타이밍 차이도 고려 | 악기 프로파일·타이밍을 고정 |

이 판단은 감독형 시험·입시 성적 산정 시스템으로 확장할 때 그대로 적용할 수 없다. 현재 계약은 `client_readable_practice`를 명시하고 정답 악보를 로컬에 가진다. UI에서 숨기는 것은 화면 정책이며 보안 경계가 아니다.

## 2. 형식과 역할

MXL은 압축된 MusicXML 악보다. 음표·리듬·박자 등의 기보 데이터이며, 파일을 받는 것만으로 소리가 나지는 않는다. [W3C MXL 설명](https://www.w3.org/2021/06/musicxml40/tutorial/compressed-mxl-files/)

권장 흐름은 다음과 같다.

```text
서버: 검증·버전 고정한 main.mxl + scale.mxl + 재생 계획 JSON
  ↓ 인증 다운로드
iPad: MXL 압축 해제·악보 해석
  ├─ 표시용 렌더러 → 정답 악보 표시(최종 제출 이후)
  └─ 정규 음악 이벤트 → 선택 마디 추출 → 로컬 MIDI/스케줄링
      → 피아노 합성 → 기기 오디오 출력

iPad: 빈 오선 위 필기 → 고정 규격 PNG 업로드
  ↓
서버: 필기 인식 → 같은 버전 MXL의 정답과 비교 → 결과 JSON
```

네트워크로 MIDI나 문제별 녹음 파일을 전달하지 않는다. 구현이 MIDI를 중간 파일로 만들든 MIDI 이벤트를 직접 스케줄하든, 아래 구간·음높이·템포 규칙은 동일해야 한다.

문제 MXL과 스케일 MXL은 별도 두 파일이다. 11개 재생 구간마다 MXL을 만들지 않는다. 첫 샘플은 8마디 문제와 2마디 상행 C Major 스케일이다.

## 3. iPad 기술 선택지

### 3.1 권장 검증 후보

SwiftUI 화면을 유지하면서 악보 엔진을 별도 모듈로 감싼다. Verovio를 WKWebView에 로컬로 포함하는 방식을 우선 검증 후보로 삼을 수 있다. Verovio는 MXL 입력과 SVG 출력·MIDI 생성을 지원하므로 표시와 재생 데이터 변환을 함께 검토하기 좋다. MXL 입력에는 압축 데이터용 API를 사용해야 한다. [Verovio 입력 형식](https://book.verovio.org/toolkit-reference/input-formats.html), [툴킷 메서드](https://book.verovio.org/toolkit-reference/toolkit-methods.html)

예상 인터페이스는 `ScoreRenderer`와 `ScorePlaybackEngine`으로 나눈다. JS/WASM/음악 폰트는 앱에 포함해 네트워크 CDN 접속 없이 준비되게 한다. 파일 다운로드는 인증 헤더가 있는 네이티브 계층에서 수행하고 검증된 bytes를 JS에 전달한다. Swift↔JS 내부 브리지에서 Base64를 사용하는 것은 가능하지만 서버 HTTP API의 응답을 Base64 JSON으로 바꾸지는 않는다.

대안인 OpenSheetMusicDisplay도 XML/MXL 로딩과 브라우저 렌더링을 제공한다. WKWebView에 표시용으로 포함하고 별도 네이티브 음악 이벤트 파서·플레이어를 연결하는 선택지가 있다. 악보 표시 라이브러리를 선택했다고 합성 재생까지 자동으로 해결되는 것으로 보지 않는다. [OSMD 시작 가이드](https://github.com/opensheetmusicdisplay/opensheetmusicdisplay/wiki/Getting-started)

이 문서는 특정 라이브러리·버전의 실기기 동작을 검증해 확정한 구현 지시가 아니다. API 계약은 엔진 교체가 가능하도록 유지하고, 아래 실기기 PoC를 통과한 버전으로 고정한다. 선택할 라이브러리·음원 리소스는 프로젝트의 배포 조건을 확인해서 적용한다.

### 3.2 재생 출력

로컬로 만든 MIDI를 재생하는 후보는 AVAudioSequencer와 AVAudioEngine/AVAudioUnitSampler 조합이다. Apple 문서에서 Sequencer는 MIDI 이벤트 트랙 재생을 제공하고 Sampler는 DLS/SF2 사운드뱅크 악기를 로드한다. 사운드뱅크 로드는 실시간 오디오 스레드 밖에서 준비한다. [AVAudioSequencer](https://developer.apple.com/documentation/avfaudio/avaudiosequencer?language=objc), [AVAudioUnitSampler 사운드뱅크 로드](https://developer.apple.com/documentation/avfaudio/avaudiounitsampler/loadsoundbankinstrument%28at%3Aprogram%3Abankmsb%3Abanklsb%3A%29)

MXL의 `midi-program=1`은 1부터 세는 General MIDI Acoustic Grand Piano다. 네이티브 Sampler의 program 값은 0부터 세므로 매핑할 때 혼동하지 않는다. 실제 DLS/SF2의 bank/program 매핑은 선택한 음원 리소스를 확인해서 `sori-piano-v1` 구현에 고정한다. 악보의 숫자를 검증 없이 그대로 Sampler 인자로 넘기지 않는다.

Verovio의 MIDI 출력은 기본 MIDI 데이터 생성이며 스피커로 소리를 내는 플레이어 자체가 아니다. 브라우저 setTimeout으로 음표마다 발음시키는 방식보다는 네이티브 시퀀서 또는 오디오 시각 기반 스케줄링을 사용한다. [Verovio MIDI 재생 설명](https://book.verovio.org/interactive-notation/playing-midi.html)

렌더러가 생성한 MIDI를 사용할 때도 프로파일을 확인하고 고정 tempo/velocity, 반복 제거, 구간 경계 정책을 지킨다. 렌더러의 기본 표현·게이트·템포가 계약과 다르면 정규 이벤트에서 MIDI를 다시 생성한다. 구현할 수 없는 경우 start 전에 준비 오류로 처리한다.

## 4. 지원하는 MusicXML 프로파일

`profile=sori-monophonic-v1`로 범위를 제한한다. MusicXML 전체 표준을 처음부터 지원한다고 약속하지 않는다. 출제 도구에서 내보낸 임의 MXL을 바로 게시하지 않고 서버에서 검증·필요한 변환을 거친다. 변환이 필요하면 **실제 게시한 변환본**이 버전 고정 원본이고 서버 채점도 그 bytes를 사용한다.

| 항목 | 허용 규칙 |
|---|---|
| 컨테이너 | MXL ZIP. mimetype, META-INF/container.xml, score.xml 세 파일 |
| 본문 | MusicXML 4.0, score-partwise, 파트 P1 하나 |
| 성부·보표 | 성부 하나, 보표 하나, 높은음자리표 |
| 조성 | 첫 버전 C Major. 임시표는 pitch/alter로 실제 음높이 표현 |
| 박자 | 일정한 4/4. 마디 길이 정확히 4개의 4분음표. 못갖춘마디 없음 |
| 길이 | main 8마디, scale 2마디. measure number는 1부터 연속 정수 |
| divisions | 480, 중간 변경 없음 |
| 템포 | 일정한 4분음표 BPM 40~200. 처음 sound tempo에 명시하고 JSON tempo_bpm과 일치 |
| 재생 | 원래 음높이, A4=440Hz, 피아노 프로파일, 일정 velocity 80 |
| 기호 | 온·2분·4분·8분음표, 점음표, 대응 쉼표, 임시표, 같은 음의 붙임줄 |
| 음높이 | MIDI 48~84 범위. 드럼·미분음·이조 악기 없음 |
| 제한 | 화음·다성부·backup/forward·연음부·꾸밈음·페르마타·스윙·페달·표현 변화 없음 |
| 반복 | 반복기호·다카포·달세뇨·코다·반복 엔딩 없음. 11개 반복은 JSON에만 정의 |
| 외부 데이터 | 외부 참조·DTD·외부 엔티티·포함 오디오·이미지 없음 |

MusicXML의 sound에는 재생 지시를 담을 수 있지만, 이 계약은 하나의 일정 템포만 지원한다. 없는 템포를 라이브러리의 임의 기본값으로 대체하지 않는다. [W3C sound 요소](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/sound/)

샘플 main에는 점4분음표·8분음표·쉼표·F#·4→5마디의 붙임줄을 포함했다. 단순히 4분음표만 잘 재생되는지 확인하는 것보다 변환 오류를 찾는 데 유용하다. 이 샘플은 계약 검증용으로 새로 만든 콘텐츠이며 실제 출시 문제를 확정한 것은 아니다.

ZIP 다운로드는 압축 1 MiB, 해제 총합 4 MiB 이내로 제한한다. 엔트리명과 container의 rootfile을 확인해 정확히 score.xml만 읽는다. 경로를 그대로 디스크에 풀지 않아도 된다. 서버와 iPad 양쪽에서 이 프로파일을 검사하고, 앱이 지원하지 않는 버전의 문제는 해당 앱에 게시하지 않는다.

## 5. 구간 생성의 수학적 규칙

음악 시간 단위 Q는 4분음표=1이다. XML의 실제 길이는 duration/divisions로 계산하고 음표 type 문자열만으로 시간을 추정하지 않는다. 점음표와 임시표·붙임줄도 해석한다. 시작과 길이는 정확한 유리수로 보관한다.

MIDI로 바꿀 때 quarter note 당 480 ticks를 사용한다. 시작과 길이를 480배 하여 정수로 표현할 수 없는 문제는 첫 프로파일에서 게시하지 않는다. MIDI C4=60 기준, BPM은 4분음표/분이다. 로컬 MIDI의 tempo 메타 이벤트 또는 네이티브 시퀀서 설정으로 이를 명시하고 이중으로 배율을 적용하지 않는다.

먼저 전체 악보의 붙임줄을 연결해 하나의 긴 note event로 합친다. 구간 a~b를 재생하려면:

```text
S = (a - 1) × 4
E = b × 4

각 이벤트의 전체 곡 시작을 t, 길이를 d라 할 때:
  잘린 시작 A = max(t, S)
  잘린 끝   B = min(t + d, E)

A < B인 이벤트만 포함
새 구간 시작 = A - S
새 구간 길이 = B - A
구간의 전체 기보 길이 = E - S
```

음표 이벤트의 note-on/note-off를 새 구간 시각에 맞춘다. 시작 이전부터 이어진 붙임줄 음은 0에서 다시 발음한다. 끝을 넘는 음은 E에서 끈다. 뒤쪽 쉼표까지 포함한 E-S 길이를 유지하므로 마지막 note-off만 보고 다음 구간으로 넘어가지 않는다. 각 구간은 앞뒤 다른 구간의 잔향·페달·활성 note를 이어받지 않는다.

샘플에서 4마디 마지막 G4가 5마디 첫 G4와 붙임줄로 연결된다. 합친 전체 이벤트는 t=15, d=2이다.

- 1~4마디: S=0, E=16 → t=15, d=1로 잘라 4마디 끝에서 끈다.
- 5~6마디: S=16, E=24 → t=0, d=1로 옮겨 5마디 첫 박에서 다시 발음한다.
- 전체 1~8마디: t=15, d=2를 그대로 1회 발음한다.

쉼표는 소리를 내지 않지만 시간 축에서는 유지한다. 샘플의 7~8마디는 7마디 앞 2박 쉼표부터 재생되므로 첫 음이 구간 시작과 동시에 나면 오류다. 선택 구간 시작에 음표가 없는 경우도 마찬가지다.

BPM=96일 때 Q 하나는 0.625초다. main 기보 길이는 32Q=20초, scale은 8Q=5초다. 각 구간의 기보 종료 뒤 note-off 감쇠 대기 300ms를 적용하고, 이어서 JSON의 구간 대기 시간을 적용한다. 실제 피아노 샘플의 물리적 잔향이 완전히 동일하다고 보장하지는 않는다. 다음 구간 전에는 활성 음·잔향 상태를 정리해 앞 구간의 음이 섞이지 않게 한다.

## 6. 표시와 필기 좌표

정답 MXL 렌더러는 화면 크기에 따라 줄바꿈·마디 폭·음표 간격을 달리할 수 있다. MusicXML을 받는다고 원래 Figma의 2단 8마디 좌표가 자동으로 재현되는 것은 아니다.

따라서 자유 필기 화면과 업로드 PNG는 **기존 고정 오선 템플릿**을 사용한다. 이 PNG는 문제 악보 파일이나 녹음 음원을 전달하는 것이 아니라 필기용 종이의 공통 배경이다. MXL 렌더러는 제출 후 정답 악보 표시 등 별도의 화면에 사용한다. 나중에 빈 오선도 MXL로 동적 생성하려면 렌더러 버전·레이아웃·마디 경계와 좌표 메타데이터를 새 계약으로 고정해야 한다.

서버의 annotations.bbox는 업로드 PNG에 대한 좌표다. 렌더링된 정답 악보 위에 같은 bbox를 바로 적용하지 않는다. 첫 버전에서는 제출 이미지+빨간 표시와 정답 MXL 뷰를 따로 보여주면 된다. 정답 악보에 주석을 달려면 추후 안정된 음표 식별자·마디/박 앵커를 추가한다.

## 7. 캐시·버전·실패 처리

main/scale MXL은 score_assets에 선언된 해시와 파일 크기로 검증하고 question_id+question_version+sha256을 키로 보관한다. 로컬 파생 이벤트와 MIDI 캐시에는 악보 해시·파서 버전·프로파일·템포·구간·악기 프로파일을 포함한다. 캐시가 오래되었다면 원본에서 다시 만들고 시험 시작 시각은 다시 설정하지 않는다.

잘못된 압축 파일·프로파일 불일치·해시 오류·음원 미준비는 start 전 앱에서 실패로 안내한다. 이런 오류를 PNG 채점 실패나 0점으로 표시하지 않는다. 시작 후 오디오가 중단되어도 필기는 보존하고 재생 계속으로 복구한다. 타이머는 기존 정책대로 계속 흐른다.

서버의 정답 이벤트는 고정 MXL을 서버 파서로 만든다. 클라이언트 파서와 독립적이므로 같은 악보에서 다른 결과를 내지 않도록 제공한 expected-events 및 실제 출제 악보를 양쪽에서 비교한다. 문제 등록 단계에서 표시·재생·채점의 이벤트 일치 여부를 확인한다.

## 8. 먼저 통과시킬 실기기 PoC

1. main/scale MXL을 기기에 로컬 포함하고 main의 8마디를 읽을 수 있게 렌더링한다.
2. 동일 파일을 서버·iPad에서 해석하여 expected-events의 MIDI 높이·시작·길이와 비교한다.
3. 앱에 선택한 피아노 리소스를 포함하고 일정 템포로 전체 문제·스케일을 재생한다.
4. 1~4, 5~6, 7~8마디를 잘라 붙임줄·쉼표 경계의 동작을 검증한다.
5. 11구간·대기 시간·중단 복귀·이어폰·기기 스피커를 확인한다.
6. 첫 구간 재생 전에 파싱·악기 로드를 마쳐 시작 지연을 측정한다.
7. 렌더링된 정답과 필기 PNG를 별도 화면으로 보여주고 채점 오버레이 위치가 유지되는지 확인한다.

이번 전달물에서 검증한 것은 MXL ZIP/XML 구조·음악 시간·예상 이벤트·해시·API 예시의 정합성이다. 실제 iPad 렌더링·MIDI 변환·음색·오디오 지연·인식 모델은 실행 검증하지 않았다. 특히 악보 렌더러·피아노 리소스는 PoC로 선택한 뒤 구현 버전을 고정해야 한다.
